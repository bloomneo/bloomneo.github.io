Founding Manifesto

Why we build
the way we build

Bloomneo builds developer tools for a world where most code is generated — a backend toolkit, a component library, and the framework that composes them into one application.

Vision

A TypeScript full-stack framework with four jobs: stay readable, keep the frontend and backend apart, run on every platform, and keep an AI agent inside the guardrails.

Most code is generated now. That changes what a framework is for — not helping you type faster, but making what arrives easy to check, hard to get wrong, and portable to wherever it has to run.

Those four jobs are the whole design. Everything else in Bloom is downstream of one of them.

What Bloom is for

Readable by whoever signs it off

Writing was never the hard part, and now that a machine does most of it that is obvious. Someone still has to put their name on a change they did not type. So where a line lives tells you what it does: a database call under src/api/ runs on the server, and there is no second reading. No tracing a directive up a component tree to answer the first question a reviewer asks.

A real line between front and back

The frontend talks to the backend over HTTP, like any other client would. That keeps them genuinely separate: either side can be rewritten, deployed or scaled without the other, and the API you already have is the one a phone app or a partner integration uses. Frameworks that blur this line buy terser code and spend the boundary to get it.

One codebase, every surface

Browser, desktop and phone from one source tree — Electron and Capacitor wrap the same web build against the same API, not three projects that resemble each other and drift. A team of three that needs a mobile app stays a team of three.

Built for an agent to work inside

An agent is fast, confident and occasionally wrong, so the job is to leave it as little to guess as possible. Conventions settle what would otherwise be a choice: a file's location is its route, one pattern instantiates every module. What it can still get wrong is caught — a wrong path is a compile error, an ungated route warns at boot. Guardrails, not guidelines.

Design principles

How we make decisions

Convention over configuration

If the right choice is obvious, it shouldn't require configuration. FBCA auto-discovers features. AppKit auto-scales. Routes auto-mount.

One pattern, everywhere

xxxClass.get() is the only way to instantiate any AppKit module. No constructors, no factories, no special cases.

Start simple, scale naturally

Memory → Redis. Local → S3. Console → Resend. Every module upgrades by setting one env var. No code changes ever.

Prefer a type to a document

Docs are read during research; mistakes happen mid-sentence. When a rule keeps being broken we move it out of prose and into the type system. Routes are a generated union, not a list in a guide.

What we refuse to build
✕
Bloat

No heavy dependencies. No features that don't earn their weight.

✕
AI overpromises

We don't claim agents write perfect code — they do not, and documentation alone has never fixed that. We make the wrong version fail immediately instead.

✕
Breaking changes without notice

Semver is a contract. We version, document, and migrate. Always.

Where we are the wrong choice

This is not for everyone

If your team is large enough that ecosystem age and hiring pool matter more than the shape of the code, use Laravel or NestJS. They have a decade of answers we do not, and that is worth more to you than anything on this page.

If you are shipping one page that will stay one page, a real client/server boundary costs more than it returns. Server actions will be less code, and they will stay less code. We are built for the app that grows a second client — and we charge you for that boundary on the first day, not the day you need it.

The one decision

Keep the boundary real

Server-side frameworks have spent a decade dissolving the line between client and server, and they got something real for it — code that reads as one program, and less of it. We went the other way, and everything on this page is downstream of that.

Because the boundary is real, the API is a real API — callable by a phone, a partner, a scheduled job. Because it is real, the web build is a real client, and bundles unchanged into desktop and mobile. Because it is real, a reviewer can tell where a line runs by where it lives.

Reviewability, reach and structural safety are not three features we shipped. They are three consequences of one decision we refused to reverse.

Our commitment

Conventions carry leverage in both directions. When one is right, every app built on Bloom is safer for it. When one is wrong, every app inherits the mistake — so the bar for an API decision here is higher than for an ordinary library, and we hold ourselves to it in public.

Where we fall short of this page, we will say so before you find it. Loud when wrong applies to us too.
