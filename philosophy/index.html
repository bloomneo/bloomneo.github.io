Founding Manifesto

Why we build
the way we build

Bloomneo builds for a world where most code is generated. Modular and consistent, so it stays reviewable. One codebase, so it ships everywhere.

Vision

Any developer. Every surface. Code you can vouch for.

Most code is now written by a machine, and the scarce thing stopped being keystrokes — it is confidence. Somebody still has to put their name on a change they did not type. We are building for that moment: a framework where the structure carries the correctness, so a reviewer can tell what a change does by where it lives, and a team of three can ship to browser, desktop and phone without becoming a team of nine.

The problems we refuse to accept

Code arriving faster than it can be reviewed

Most code is now generated, and the bottleneck moved from writing to signing off. A reviewer's first question — does this run on the server? — should be answered by where the file sits, not by tracing directives up a component tree.

Safety you have to remember

An auth check repeated in every handler is a check that will eventually be missed, and the one that is missed does not announce itself. Correctness belongs in the structure, where a handler written next month inherits it.

Web-only by default

A team that needs a desktop app or a phone app should not become three teams. Collapsing the client/server boundary buys terse code and costs every surface that is not a browser.

Failures that say nothing

A wrong path that 404s, a config that returns HTML instead of JSON, a file the router silently ignores. Silence is the most expensive failure there is — and for an agent, whose whole debugging loop is the error message, it is total.

Core values

What we stand for

Correct by default

The safe version is the shape of the file, not a discipline you remember. The auth gate lives on the router, so a handler added next month inherits it. The role check lives on the layout, so a page added later cannot forget it. Ownership belongs in the WHERE clause, not a separate check. These are not conveniences — they are categories of bug that cannot occur.

Reviewable

Where a line lives tells you what it does. A database call in src/api/ runs on the server; there is no second reading, no tracing a directive up the component tree. When most code arrives pre-written, you are no longer reading to recall your own intent — you are auditing someone else's, at volume. Every question the structure answers for free is one you do not have to re-derive.

One codebase, every surface

The client/server boundary is real, so the API is a real API — callable by a phone, a partner, a cron job — and the web build is a real client, bundled unchanged into desktop and mobile. Browser, Electron, iOS and Android from a single source tree. Not four projects that resemble each other.

Loud when wrong

A mistake should fail immediately and point somewhere small and true. A wrong route is a compile error. A misconfigured API base says so instead of throwing a JSON parse error. A route file the router will never mount warns at startup rather than quietly 404ing. Silence is the most expensive failure mode there is — for a person, and far more so for an agent, whose entire debugging loop is the error message.

Autonomy

Loosely coupled by design. Use AppKit without UIKit. Use UIKit without Bloom. Take what you need — nothing forces you to take everything.

Open

MIT licensed. No vendor lock-in, no hidden tiers. The framework is the product, not the pricing page.

Design principles

How we make decisions

Convention over configuration

If the right choice is obvious, it shouldn't require configuration. FBCA auto-discovers features. AppKit auto-scales. Routes auto-mount.

One pattern, everywhere

xxxClass.get() is the only way to instantiate any AppKit module. No constructors, no factories, no special cases.

Start simple, scale naturally

Memory → Redis. Local → S3. Console → Resend. Every module upgrades by setting one env var. No code changes ever.

Minimal code, maximum intent

One method that does the right thing beats four that cover every edge case. Purposeful APIs with smart defaults — no bloat.

Prefer a type to a document

Documentation is consulted during research. Mistakes happen mid-sentence, when the writer is confident and does not stop to check — and no document intercepts that. When a rule keeps being broken, we promote it out of prose and into the type system, where it is checked at the moment the wrong thing is written. Routes are generated into a union, not listed in a guide.

What we refuse to build
✕
Bloat

No heavy dependencies. No features that don't earn their weight.

✕
Tight coupling

Modules must stay independent. A change in one never breaks another.

✕
AI overpromises

We don't claim AI generates perfect apps. We make AI agents reliably correct on our APIs.

✕
Paywalled core features

Everything fundamental is open source. If you need it to build, you get it free.

✕
Breaking changes without notice

Semver is a contract. We version, document, and migrate. Always.

✕
Vendor lock-in

Switch databases, email providers, or storage backends by changing an env var. We never own your infrastructure choices.

The one decision

Keep the boundary real

Server-side frameworks have spent a decade dissolving the line between client and server, and they got something real for it — code that reads as one program, and less of it. We went the other way, and everything on this page is downstream of that.

Because the boundary is real, the API is a real API — callable by a phone, a partner, a scheduled job. Because it is real, the web build is a real client, and bundles unchanged into desktop and mobile. Because it is real, a reviewer can tell where a line runs by where it lives.

Reviewability, reach and structural safety are not three features we shipped. They are three consequences of one decision we refused to reverse.
